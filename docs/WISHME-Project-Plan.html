1. Motive — what this product is for

WISHME is not a greeting-card shop and not a chat app. It is a personalized digital keepsake under LIWAAS. A forwarded WhatsApp wish disappears. WISHME is for the birthday, rakhi, anniversary or blessing you want someone to reopen.

The person who loves someone (the customer) makes a private experience: their person’s name, photographs, a letter, video, a song. They publish it. The person who receives it (the recipient) opens a unique link or scans a QR and sits in a small world for a few minutes — like a letter, not a notification.

You (LIWAAS) run the admin studio: customers, wishes, templates, plans. WISHME should feel emotional, celebratory and premium: cream, navy #0b1f3a, gold #c4a35a — different from LIWAAS ecommerce.

The product loop (this is the whole project)
Choose occasion → choose template → edit content → save draft → pay if premium → publish → unique 22-character link / QR → recipient opens a private animated wish (about 2–3 minutes) → link can expire, wait for a scheduled time, or ask for a password.

Until that loop works with real saved data, the product is not finished. Screens and auth are the house. The loop is the product.

3. How to read the steps

Do them in order unless you choose to skip a small auth UI item. Each step says: goal, details, APIs, screens, and “done when”. Do not start Razorpay or extra templates before a customer can save and publish at least one Midnight Toast wish with their own photos.

Next action after this document: Step 2 (catalog APIs) then Step 3 (editor). Step 1 (profile / forgot password) can sit beside that if you want accounts nicer first — it is not the product loop.

4. All steps — foundation to launch

Step 0 — Foundation Done

Goal. A professional, responsive house ready for modules.

  • React + TypeScript + Vite + Tailwind, React Router, TanStack Query, Zustand, GSAP.
  • Laravel REST API, Sanctum, hashed passwords, roles customer / admin.
  • Public marketing site with real photography and copy.
  • Dashboard + admin layouts, reusable UI kit.
  • Midnight Toast as the quality bar for a recipient wish.
  • Folder structure split by public / auth / customer / admin / wish + services.
  • Real login (demo cards removed). Copy says Admin, not Staff.

Done when. Already true as of 6 Sep 2026.

Step 1 — Finish the account API ready · UI missing

Goal. A customer can edit profile and recover a password. An admin can do the same.

Details

  • Profile form: name, email, mobile, date of birth. Call existing PUT /profile. Password change with confirmation.
  • Forgot password screen from login. Call POST /forgot-password. Then reset screen with 6-digit OTP + new password (POST /reset-password).
  • Send OTP by email (or SMS) — today it only logs. Without this, reset is not usable in production.
  • Register may later collect mobile (API already allows it).

APIs. Already exist. Add mail/SMS. Do not invent new auth endpoints unless needed.

Screens. Customer profile, admin profile, forgot, reset.

Done when. A real user can change name, request OTP, set a new password, and sign in again.

Step 2 — Catalog (occasions + templates) from the database Do next with Step 3

Goal. Home, gallery, and create-flow read occasions/templates from the API. Admin can add or edit them later.

Details

  • Tables: occasions, templates (name, occasion, description, cover, premium flag, config JSON for rooms/fields).
  • Seed the four live occasions: Birthday, Anniversary, Raksha Bandhan, Bhai Phota.
  • Seed the eight gallery templates (see section 6). Mark Midnight Toast as the first with a full experience config.
  • Public GET endpoints. Admin POST/PUT later in Step 7 if needed.
  • Frontend: catalog.service.ts already has getOccasions / getTemplates — switch from mock files to these APIs.

Done when. Changing a template in the database changes the website gallery without a frontend code edit.

Step 3 — Create a wish (the editor) Core product · do next

Goal. After occasion + template, the customer fills the keepsake and saves a draft.

This is the original “do not build yet” item from day one. It is now the main remaining work.

Details

  • Keep Step 1 of create-project (occasion → template). Add Step 2: editor.
  • Fields (from the original brief): recipient name, titles, messages/letter, images, videos, music, plus template-specific rooms (for Midnight Toast: letter, stories, moments, privacy, gift).
  • Uploads go to storage (S3 or local disk first). Save URLs on the project.
  • Autosave draft. List on My Projects and Overview.
  • Preview: open the wish player with draft data (not the public token yet).
  • Do one template fully: Midnight Toast. Other templates can show “editor coming” until Step 8.

APIs (new).

  • POST /projects — create draft (template_id, occasion).
  • GET /projects — customer’s list.
  • GET /projects/{id} — one project + content.
  • PUT /projects/{id} — save editor fields.
  • POST /projects/{id}/media — upload photo/video/audio.

Screens. Create flow, editor, My Projects (real rows), Overview counts.

Done when. A logged-in customer can pick Midnight Toast, add Riya’s name, a letter, photos and a song, save, leave, come back, and still see it.

Step 4 — Publish, token, time window, password, schedule After editor

Goal. A draft becomes a live private wish the recipient can open.

Details

  • Publish generates a random 22-character token. URL: wishme.liwaas.com/w/{token}.
  • Wishing date/time is stored. Link is valid for 72 hours after that moment (already the frontend rule). Expired → closed screen.
  • Invalid token → closed screen.
  • Optional password (Signature feature). Recipient types it before the gate.
  • Scheduled unlock: publish now but gate stays closed until wishing datetime.
  • Statuses: draft · scheduled · published · expired.
  • WishExperiencePage loads project by token from API, not demoWishes.ts.

APIs (new).

  • POST /projects/{id}/publish — body: wished_at, ttl_hours (default 72), password optional.
  • GET /w/{token} public — returns content if open; 404/410 if invalid/expired; 401 if password required.
  • Unpublish / extend later if needed.

Done when. Customer publishes; recipient opens the real link on a phone and sees that customer’s photos and letter. After 72 hours the same link is closed.

Step 5 — Share pack (link + QR) After publish

Goal. Customer can copy the link and download a QR card to print or send.

  • On the project page after publish: copy link, download QR (PNG/PDF), optional password reminder.
  • QR encodes the full URL. Style: navy/gold, WISHME wordmark, recipient first name.
  • Promised on Signature in the pricing copy — still show copy-link on free if you allow free publish of core templates.

Done when. Scanning the QR on a phone opens the live wish.

Step 7 — Live admin studio Needs real customers + wishes

Goal. Admin sees real people and real wishes, not dummy cards.

  • Replace admin.service.ts dummy lists with APIs: customers, wishes, stats.

  • Optional: create admin users, disable a customer, take a wish down.
  • Use existing role middleware. Never show admin routes to customers.

Done when. After a test customer publishes, the wish appears on /admin/wishes with the right name and status.

8. Design and build rules (do not drop these)

  • Emotional, premium, clean. White/cream, navy text, gold accent. Soft shadows, rounded cards. Mobile first.
  • TypeScript, no any. Small reusable components. Mock/API data in services, not copied into every page.
  • Do not add libraries without need. Payments = Razorpay only when Step 6 starts.
  • Recipient page must work on a phone. Aim for 2–3 minutes of real content per template.
  • Private unique link — not a public feed of wishes.
  • Log every create/move/update in PROJECT_UPDATES.txt.
